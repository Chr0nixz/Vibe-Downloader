# Vibe Downloader 功能与页面构想

最后更新：2026-09-13  
适用版本：`0.5.0`  
关联文档：[当前不足与改进建议](project-current-improvement-review.md)、[项目改进审计](project-improvement-audit.md)、[产品约束](../PRODUCT.md)、[设计约束](../DESIGN.md)

## 1. 文档目的

本文不是当前实现清单，也不是把路线图中的计划写成已完成能力。它回答三个问题：

1. 在现有下载、队列、诊断和浏览器交接基础上，还能增加哪些真正有用的功能？
2. 哪些页面可以让用户更容易理解、控制和恢复下载？
3. 如何做出区别于传统 IDM 和普通“链接转文件”工具的产品特色？

项目不应靠堆更多协议入口来制造丰富感。更有价值的方向是让用户始终知道：任务现在发生了什么、为什么变慢或失败、还能否安全续传、下一步应该做什么，以及文件最终是否值得信任。

## 2. 产品特色建议

### 2.1 核心差异化：从“下载器”变成“下载控制台”

传统下载器主要展示速度、进度和暂停按钮。Vibe Downloader 可以把差异化集中在四个可感知的承诺上：

| 特色承诺 | 用户看到的结果 | 技术基础 |
| --- | --- | --- |
| 可解释 | 不只显示“速度慢”，还说明是服务器限速、代理等待、连接不足、磁盘写入慢还是远端拒绝。 | request diagnostics、scheduler snapshot、speed history、磁盘统计。 |
| 可恢复 | 失败不是终点，而是给出“重试、换镜像、重新探测、重新认证、释放空间、从安全点重启”等具体动作。 | 稳定错误码、任务状态机、恢复动作、引擎生命周期。 |
| 可验证 | 下载完成后能说明文件是否经过校验、远端是否变化、哪些分片被续传、是否存在未清理的临时物。 | checksum、validator、segment/work unit、staging manager。 |
| 可控 | 队列、限速、代理、保存目录和浏览器交接都能预览影响，并可批量管理。 | 统一 CreateDraft、task proxy、priority、scheduled window、browser handoff。 |

这四点比“再支持十种协议”更容易形成产品记忆，也与当前“可靠优先、专家深度按需展开”的产品约束一致。

### 2.2 特色一：下载健康卡（Download Health Card）

每个任务显示一个简短的健康摘要，而不是让用户自己阅读一堆状态字段：

- `健康`：服务器允许 Range，连接稳定，磁盘速度充足，最近没有重试。
- `受限`：服务器只允许单连接、代理延迟较高、服务端限速或当前连接槽不足。
- `需关注`：远端文件可能变化、校验和未通过、凭据失效或磁盘空间不足。
- `不可恢复`：当前分片计划、协议能力或权限不允许安全续传。

健康卡必须解释依据，例如“最近 5 分钟平均速度下降 62%，服务器响应时间未变，疑似本地磁盘写入瓶颈”。它不是一个神秘分数，而是由可观察指标组成的结论。

建议使用离散状态和文字原因，不使用 0～100 的伪精确分数。若未来引入分数，必须同时显示构成项和置信度。

### 2.3 特色二：恢复剧本（Recovery Playbook）

当任务进入 `NeedsAttention` 或持续异常时，显示一组按风险排序的恢复方案：

1. **安全重试**：保留已完成字节和当前 validator，使用相同路径恢复。
2. **重新探测**：重新检查远端大小、Range、认证和代理，不立即覆盖本地文件。
3. **切换镜像**：仅对有可靠校验或稳定分片计划的 Metalink 任务启用。
4. **重新认证**：只更新凭据，不重置已经完成的分片。
5. **修复分片**：只重新下载校验失败或响应不完整的范围。
6. **从头开始**：明确说明将删除哪些临时文件和已下载字节，并要求确认。

每个动作都应显示“会保留什么、会删除什么、是否需要重新下载、是否可能改变最终路径”。这样可以把当前分散在错误码、右键菜单和恢复对话框里的知识变成一个可理解的流程。

### 2.4 特色三：文件完整性护照（Integrity Passport）

完成任务后提供一份可复制或导出的简短证明：

```text
File: ubuntu.iso
Source: https://example.com/ubuntu.iso
Downloaded: 2026-09-13 18:42
Bytes: 4.7 GiB
Resume: 3 checkpoints, 2 resumed ranges
Remote validator: ETag matched
Checksum: SHA-256 matched
Staging cleanup: complete
```

它可以用于系统镜像、模型文件、游戏安装包、数据集等用户特别在意的文件。对于没有远端 checksum 的任务，应明确写“未提供远端校验和”，而不是显示绿色“已验证”。

建议支持三种输出：

- 任务详情中的紧凑摘要；
- 脱敏后的文本报告；
- 带文件 hash 的 JSON，供脚本或归档系统使用。

该功能的价值在于把“下载完成”与“文件可信”区分开来，是一个比普通进度条更有辨识度的产品能力。

### 2.5 特色四：可解释的队列自动驾驶

增加一个可选的“队列策略”而不是简单增加并发数：

- **均衡模式**：在不同主机之间平均分配活动任务。
- **专注模式**：优先完成最接近结束的任务，减少同时打开的文件数。
- **吞吐模式**：优先使用支持 Range 的大文件和空闲主机槽。
- **省电模式**：降低轮询频率、限制并发和完成动作，适合笔记本电池。
- **夜间模式**：遵循计划窗口和限速，完成后不执行高干扰动作。

策略切换必须显示实际影响，例如“最多 2 个活动任务，每主机 1 个连接，夜间限速 5 MiB/s”。策略只是对现有 scheduler 参数的组合，不应另写一套绕过状态机的调度器。

### 2.6 特色五：安全的浏览器“收件箱”

当前浏览器 handoff 主要是把链接交给下载器。可以增加一个本地收件箱，让用户先审阅再创建任务：

- 显示来源页面、URL、文件名、协议、预计大小和发现时间；
- 自动合并短时间内重复的链接；
- 允许批量选择、设置预设、指定分类和保存目录；
- 对预签名 URL、嵌入凭据、跨域 header 和私网地址显示安全提醒；
- 支持“只加入队列，不立即下载”；
- 对过期的 handoff 提供重新从浏览器发送的入口。

收件箱应只保存必要的脱敏信息，并提供 TTL 和一键清空，不能演变成永久保存 Cookie 或 token 的历史库。

## 3. 建议新增的页面

### 3.1 下载总览页（Mission Control）

这是一个真正可操作的工作台，不是营销首页，也不是一组装饰性卡片。

**首屏布局：**

```text
┌────────────────────────────────────────────────────────────┐
│ 当前速度  预计完成  活动任务  需关注  可用磁盘               │
├────────────────────────────────────────────────────────────┤
│ 需要处理的任务                │ 队列即将发生什么            │
│ [错误/认证/空间/远端变化]      │ [下一个任务/计划/限速]       │
├────────────────────────────────────────────────────────────┤
│ 最近活动与速度趋势                                         │
├────────────────────────────────────────────────────────────┤
│ 任务列表（与主列表使用相同查询和选择模型）                  │
└────────────────────────────────────────────────────────────┘
```

**应有功能：**

- 只显示需要决策的摘要，不复制全部任务列表逻辑；
- “需关注”直接进入恢复剧本；
- 速度趋势可切换 15 分钟、1 小时、1 天；
- 所有数字可点击回到对应筛选结果；
- 无活动任务时显示最近一次下载结果和快速新建入口；
- 支持窄窗口堆叠布局，不使用大面积 hero 或卡片网格。

**建议：**作为现有 `all` 视图的增强模式，而不是强制新增一个一级导航项。默认用户仍应尽快看到任务列表。

### 3.2 存储与清理中心

这是当前最有必要新增的运维页面之一。

**页面区域：**

- 按保存目录显示总空间、已用空间、可用空间和预计可完成任务数；
- 临时文件分类：HTTP `.part`、Metalink `.part-N`、HLS/DASH staging、失败任务残留、孤儿目录；
- 按任务查看文件归属、最后更新时间和是否可以安全删除；
- “只清理孤儿”“只清理已取消任务”“清理全部可回收物”三个明确动作；
- 清理前显示空间回收量和不可恢复提示；
- 启动时清扫结果和最近一次自动清理记录。

**安全要求：**

- 后端返回文件清单和关联任务，前端不能自行拼接路径；
- 只允许删除应用 staging 根目录和已确认的任务路径；
- 删除中的任务必须先进入稳定状态，不能边写边删；
- 清理失败按文件逐项报告，不把部分成功显示成全部成功。

### 3.3 恢复中心（Recovery Center）

将 `Attention Center` 从“异常列表”提升为“异常处理工作区”。

**核心能力：**

- 按原因分组：认证、代理、网络、空间、远端变化、校验、协议不支持、内部错误；
- 每组显示受影响任务、预计可自动恢复数量和需要用户输入的数量；
- 支持批量安全重试，但对“从头开始”“删除临时文件”单独确认；
- 允许先修复共享问题，例如一次更新凭据或代理后重试一组任务；
- 展示恢复历史，记录谁在何时执行了什么动作。

**与现有页面的关系：**

- 保留 Attention Center 的轻量入口和通知徽标；
- 复杂处理放入 Recovery Center；
- Task Details 仍保留单任务的上下文和原始诊断。

### 3.4 队列规划页（Queue Planner）

Queue Center 当前适合即时重排；Queue Planner 适合计划未来几小时或几天的任务。

**建议功能：**

- 时间轴显示下载窗口、限速段、预计完成时间和队列顺序；
- 拖动任务到时间段时显示预计影响，不直接绕过调度器；
- 按优先级、主机和分类过滤；
- 保存“工作日”“夜间”“移动网络”等队列预设；
- 显示计划冲突，例如“当前窗口只有 1 小时，但预计需要 3 小时”；
- 支持“窗口结束时暂停”“完成后保持队列”“完成后执行动作”等明确选项。

**实现原则：**复用现有 scheduled window、priority、speed limit 和 completion action 数据模型，避免形成第二个调度配置体系。

### 3.5 网络与连接实验室（Network Lab）

这是面向高级用户的只读诊断页，不应默认打扰普通用户。

**可视化内容：**

- 每个任务的连接数、主机槽位、代理路径和当前吞吐；
- DNS、TCP/TLS、首字节和连续读取耗时；
- HTTP Range、ETag、If-Range、Retry-After 和重定向结果；
- 服务器限速与本地磁盘写入速度对比；
- 最近 10 次请求的状态码和重试原因；
- BT peer/tracker、HLS/DASH 分片、Metalink 镜像健康度。

**特点：**将“为什么慢”转化为证据链。所有敏感 header、URL query、Cookie 和凭据默认脱敏，导出报告也使用同一脱敏逻辑。

### 3.6 下载历史与统计页

关注趋势和决策，不做复杂 BI：

- 每日/每周下载量、完成数、失败数、平均速度和平均重试次数；
- 按协议、主机、分类和保存目录筛选；
- “最常失败的原因”和“最常受限的主机”；
- 成功率应区分任务数和字节数，避免小文件数量掩盖大文件失败；
- 支持脱敏 CSV/JSON 导出；
- 图表时间范围和采样粒度受控，避免对 task_events 做无界全表扫描。

### 3.7 备份与迁移中心

与 Settings 中的单次备份按钮相比，独立页面可以让迁移行为更清楚：

- 备份内容预览：任务、文件清单、设置、分类规则、站点规则、校验记录；
- 明确标出不会导出的内容：OS keyring 中的全局代理密码、不可迁移的机器绑定密文；
- 恢复前检查版本、磁盘空间、路径策略和 settings 白名单；
- 恢复后列出需要重新配置的代理、凭据、ffmpeg 和保存目录；
- 支持只恢复任务、只恢复规则、只恢复设置等安全子集；
- 显示跨卷复制、校验和和回滚结果。

### 3.8 任务预设与站点规则中心

把“任务预设”和“站点规则”放到一个有明确关系的配置页面：

- 预设：保存目录、分类、优先级、限速、代理、校验和、完成动作；
- 站点规则：按 host、扩展名、MIME、大小和 URL 匹配；
- 规则命中预览：输入 URL、文件名、MIME、大小后显示最终分类和预设；
- 冲突分析：显示多条规则的优先级和最终胜者；
- 导入导出前显示规则数量、版本和潜在敏感字段；
- 支持“仅对浏览器 handoff 生效”与“对手动/剪贴板创建生效”的范围选择。

这能把当前已有的 Site Rules、Classification Rules 和 CreateDraft 组合成用户容易理解的自动化能力。

### 3.9 浏览器集成中心

虽然当前已有设置控件，但可以把浏览器集成做成完整的配置与诊断页面：

- Chrome/Edge/Firefox 安装状态和版本；
- Native Messaging manifest 路径、连接状态和最近一次 handoff；
- release/candidate/dev profile 的权限差异；
- 手动发送测试链接、检查 request ID 去重和单实例转发；
- 过期 header 恢复；
- 明确列出不会做的事情：不会读取浏览器保存密码，不会控制本地保存路径，正式包不会自动接管全部下载；
- 一键打开日志和修复建议。

## 4. 现有页面的特色化完善

### 4.1 New Download：从“输入框”变成“下载计划预览”

在开始按钮前显示一个紧凑的计划摘要：

```text
目标       ubuntu.iso · 4.7 GiB
保存到     D:\Downloads\ubuntu.iso
连接       Range · 4 segments · max 8 per host
代理       Off
校验       SHA-256 expected
冲突       文件已存在，将自动重命名为 ubuntu (1).iso
```

建议增加：

- URL、文件名、保存路径、代理、凭据和校验和的最终快照；
- 探测阶段的“可续传/仅单流/未知大小/需要认证”标签；
- 服务器返回多个文件或媒体轨道时的选择摘要；
- 同名文件和重复 URL 的处理策略预览；
- “加入队列”“立即开始”“仅保存计划”三个动作；
- 批量导入去重、无效行、重复行、已存在任务和预计总大小的统计。

### 4.2 Task List：让大量任务更像工作台

- 保存常用筛选视图，例如“本周失败”“大于 1 GiB 且未校验”“当前主机”；
- 可选列：健康、代理、校验、预计完成、连接数、最近错误；
- 批量编辑分类、优先级、限速、保存目录和完成动作；
- 对完整查询集合执行全选，而不是只选当前已加载页；
- 拖放排序时显示插入位置和失败回滚；
- 记住列宽、排序、筛选和详情面板宽度，但提供恢复默认布局；
- 允许“复制为任务预设”，把选中任务的配置转换成可复用模板。

### 4.3 Task Details：加入任务时间线和决策上下文

建议把现有 Chunks/Connections/Requests/Logs 旁增加 Overview 时间线：

- 创建、探测、排队、开始、限速、暂停、恢复、重试、校验、发布和完成时间；
- 每次状态变化的原因和触发来源（用户、调度器、远端、内部错误）；
- 最近一次安全 checkpoint 和可恢复范围；
- 远端 validator、文件大小变化和 checksum 结果；
- 预计还需时间以及估算依据；
- “复制完整脱敏诊断”“执行恢复剧本”“打开存储位置”快捷动作。

### 4.4 Queue Center：从重排列表变成资源编排

- 顶部显示活动任务槽、主机槽和全局限速剩余量；
- 每个队列项显示等待原因，而非只有 queued 状态；
- 支持按主机和优先级折叠；
- 展示“为什么不是下一个任务”：优先级、计划窗口、主机槽、代理/凭据或重试时间；
- 重排失败自动恢复服务器顺序并保留错误提示；
- 提供“只运行当前选择”“暂时释放一个主机槽”等明确的临时动作。

### 4.5 Attention Center：从通知列表变成批处理工作区

- 按可共享的修复原因聚合任务；
- 修复代理/凭据后自动刷新可恢复任务；
- 对每个批量动作显示成功、跳过、失败三类数量；
- 将无法安全自动恢复的任务单独列出，不提供误导性的“一键全部重试”；
- 支持导出失败摘要，包含稳定错误码和脱敏上下文。

### 4.6 Settings：从 11 个折叠区变成“配置影响地图”

- 页面顶部显示未保存更改和影响范围；
- 修改全局代理、限速、计划窗口或完成动作时，显示会影响哪些任务；
- 每个设置提供默认值、当前值、作用范围和重启要求；
- 将“下载”“网络”“浏览器”“安全”“外部工具”“数据”分组，减少跨区寻找；
- 每一项支持恢复默认，但危险设置和密钥相关设置需要明确确认；
- 导入设置前显示 diff，而不是直接覆盖。

### 4.7 Environment：从一次检查变成持续健康状态

- 每项显示“已检查时间”和数据来源；
- 区分自动修复、需要用户操作、需要重启和无法由应用修复；
- 保存目录显示实际可写性、剩余空间和是否跨卷；
- ffmpeg 显示版本、路径和支持的 remux 能力；
- 浏览器集成显示 manifest、bridge、扩展和权限是否一致；
- 支持复制脱敏报告，并在报告中标注未知项而不是猜测为正常。

## 5. 可增加的后台能力

### 5.1 分片级修复

对于有可靠分片计划和 checksum 的任务，允许只重下载损坏范围：

1. 找出校验失败的分片或 byte range；
2. 保留未损坏数据和原始文件路径；
3. 重新探测并确认远端大小/validator；
4. 只替换受影响的范围；
5. 再次校验后原子发布。

这是比“整个文件重新下载”更有特色、也更适合大文件的恢复能力。但无可靠边界或远端已变化时必须拒绝并建议从头开始。

### 5.2 预估完成时间的置信区间

不要只显示一个容易失真的 ETA，可以显示：

- 基于最近 30 秒速度的短期 ETA；
- 基于最近 5 分钟稳定速度的长期 ETA；
- 当速度波动、服务器限速或队列窗口不稳定时显示“估算不稳定”。

估算应考虑排队时间、计划窗口、限速、主机槽和校验阶段，而不是简单用剩余字节除以瞬时速度。

### 5.3 网络恢复编排

系统从离线恢复、代理恢复或网络切换后，按照优先级和主机分批唤醒任务：

- 先恢复可安全续传的任务；
- 对同一主机设置重连间隔；
- 对 429/503 遵守 Retry-After；
- 对需要认证或远端变化的任务不自动重试；
- 在 UI 显示“正在分批恢复，避免同时重连”。

### 5.4 磁盘预算与提前保护

下载前估算最终文件、临时分片、staging、校验和重试所需空间，给出：

- 当前可用空间；
- 任务预计峰值空间；
- 同目录其他活动任务的占用；
- 预计不足时间；
- 可安全回收的临时空间。

空间不足时应优先暂停并保护已有文件，不应等写入失败后才显示错误。

### 5.5 任务包和跨设备迁移

支持导出一个不含明文凭据的任务包：

- URL、任务状态、分片计划摘要、校验和、分类和目标文件名；
- 可选排除 query token、Cookie 和 Basic Auth；
- 目标设备恢复时重新选择保存目录和本地凭据；
- 对不能安全复用的 checkpoint 明确标记为“仅恢复任务配置”；
- 提供版本兼容和迁移报告。

### 5.6 本地自动化接口

稳定性和安全边界完成后，可以提供本地 CLI/JSON-RPC：

- 创建、查询、暂停、恢复、删除、导出任务；
- 查看队列、健康和诊断摘要；
- 订阅状态事件；
- 默认只监听本机；
- 使用短期 token、权限范围和请求配额；
- 与 UI 使用同一命令、状态机和错误码。

不要先做远程 REST 服务。远程访问会扩大凭据、文件路径和命令执行的攻击面，当前产品没有这个必要。

## 6. 中长期产品方向

### 6.1 媒体任务工作流

在基础 HLS/DASH 稳定后，可以增加媒体任务向导：

- 识别 master playlist、视频、音频和字幕候选；
- 显示分辨率、编码、码率、语言和预计大小；
- 选择音轨/字幕后预览最终输出；
- 对不支持的 DRM、SAMPLE-AES、动态 MPD 和跨源凭据明确拒绝；
- 将最终选择保存为媒体任务预设。

重点是“可解释的选择”，不是偷偷抓取网页视频。浏览器权限和站点策略必须保持现有安全边界。

### 6.2 云盘与远程存储

云盘解析、账号同步、WebDAV 扩展、S3/对象存储等功能应等到凭据、代理、限速和恢复契约统一后再开始。建议先从单一 provider 的只读文件列表和下载开始，避免一开始就做复杂双向同步。

### 6.3 插件协议

插件系统可以支持新的解析器或协议，但必须：

- 插件与主进程隔离；
- 明确网络、文件和凭据权限；
- 有版本化能力描述和稳定错误码；
- 不允许插件绕过统一代理、SSRF 和文件提交路径；
- 有签名、来源和卸载清理机制。

在这些条件满足前，不建议做“任意脚本插件”或下载社区插件市场。

## 7. 推荐落地路线

### 阶段 0：先修基础契约

目标：不让新页面掩盖旧问题。

- 完成 `ARC-32`、`ARC-33`、`ARC-37`、`ARC-38` 等 P0/P1 生命周期修复；
- 统一网络客户端、代理、SSRF、超时、凭据 origin 和取消语义；
- 修复 Metalink/DASH/BT 的分片、session、恢复和清理问题；
- 把稳定错误码、诊断字段和资源清理做成页面可消费的后端契约。

### 阶段 1：先做闭环页面

推荐顺序：

1. 存储与清理中心；
2. 恢复中心；
3. 备份与迁移中心；
4. 浏览器集成中心；
5. Task Details 时间线与完整性护照。

原因是这些页面直接利用现有数据和命令，能够立刻降低故障处理成本，不需要先扩展新的协议。

### 阶段 2：做可复用的高频效率

1. 任务预设与站点规则中心；
2. New Download 计划预览；
3. Task List 保存筛选、批量编辑和列配置；
4. Queue Planner 和队列策略；
5. 下载健康卡。

### 阶段 3：做特色能力

1. 下载总览 Mission Control；
2. 网络与连接实验室；
3. 分片级修复；
4. 网络恢复编排；
5. 历史统计和完整性报告。

### 阶段 4：扩展产品边界

在前面阶段有稳定测试、性能基线和权限模型后，再考虑：

- 本地 CLI/JSON-RPC；
- 媒体任务向导；
- 云盘/对象存储；
- 插件协议；
- Safari 和正式浏览器分发。

## 8. 建议的数据和架构增量

### 8.1 新增统一的任务健康模型

建议后端返回结构化 `TaskHealthSummary`，而不是让前端从多个字段猜测：

```ts
type TaskHealthSummary = {
  level: "healthy" | "limited" | "attention" | "blocked";
  primaryReason:
    | "server_limit"
    | "network_unstable"
    | "proxy"
    | "disk"
    | "remote_changed"
    | "checksum"
    | "credentials"
    | "unsupported"
    | "internal";
  confidence: "high" | "medium" | "low";
  actions: Array<"retry" | "probe" | "credentials" | "proxy" | "free_space" | "restart">;
  updatedAt: string;
};
```

健康模型只能由后端基于真实观测生成，前端不应根据错误字符串重新分类。

### 8.2 引入事件时间线而非重复写 UI 状态

现有 task events、request diagnostics 和状态转移可以整理为统一的只读 timeline projection：

- 事件类型、时间、任务 ID、来源和稳定 code；
- 脱敏的参数摘要；
- 是否影响可恢复性、是否需要用户操作；
- 用 cursor 分页，保留年龄和数量上限。

这样 Task Details、Recovery Center、History 和诊断导出可以共享同一数据源。

### 8.3 增加资源生命周期管理器

为 staging、part、temp、ffmpeg、BT session 和 worker 建立统一的 owner/cleanup contract：

- 创建时登记 owner 和路径；
- 运行中报告状态；
- 成功、失败、取消、删除、重启和启动清扫都走同一 cleanup API；
- 记录清理结果和重试次数；
- 页面只读展示，不直接操作未登记路径。

这既支撑 Storage Center，也能减少 `ARC-23`、`ARC-24`、`ARC-38`、`ARC-47` 一类问题反复出现。

### 8.4 统一脱敏报告协议

健康卡、网络实验室、完整性护照、浏览器集成和 Environment 都需要导出报告。建议后端统一定义：

- URL query 默认移除；
- `Authorization`、`Cookie`、代理密码、私钥和 token 永不输出；
- 本地路径可选择保留文件名、隐藏用户名和盘符；
- 原始 code 保留，原始英文 message 只放 debug 日志；
- 导出报告带 schema/version，便于后续兼容。

## 9. 页面质量标准

每个新增页面至少满足以下要求：

1. 有明确的空状态、加载状态、错误状态、部分成功状态和权限提示。
2. 所有异步操作都有取消、重试或恢复入口，不能只显示 spinner。
3. 不复制另一套任务/队列/设置状态，优先复用现有 store 和查询模型。
4. 所有危险动作显示影响范围，并使用确认或 Undo。
5. 键盘可完成主要流程，列表、表单和错误文案符合统一 ARIA 模型。
6. 关键数字可以追溯到任务、请求、事件或文件，不显示无法解释的评分。
7. 页面默认保持密集、安静、可扫描；高级诊断通过展开、详情或实验室页面呈现。
8. 异常和敏感数据遵守统一错误码、SSRF、代理、header origin 和脱敏协议。
9. 前端至少有交互测试，后端至少有一个真实集成场景；涉及文件、网络、恢复或并发时不能只测 mock 组件。
10. 页面关闭、任务删除、应用退出和重启后不留下轮询、监听器、worker、临时文件或 pending toast。

## 10. 最值得优先做的五项

如果只能选择五项，建议是：

1. **存储与清理中心**：直接解决 staging/part/孤儿文件的可见性和空间风险。
2. **恢复中心 + 恢复剧本**：把失败从“红色状态”变成可执行的处理流程。
3. **Task Details 时间线 + 完整性护照**：建立“发生了什么”和“文件是否可信”的证据链。
4. **New Download 计划预览 + 任务预设**：减少创建前的不确定性，提升重复下载效率。
5. **下载健康卡 + 网络实验室**：形成“可解释下载”的产品识别度。

这五项共同使用现有数据和引擎，不要求立即增加云盘、插件或远程控制等高风险边界，却能让 Vibe Downloader 从“功能较多的下载管理器”变成“能解释、能恢复、能证明结果的下载控制台”。
