# Vibe Downloader 项目不足与改进审查

本文档基于当前代码库状态，从以下四个维度整理项目现有不足和可改进方向：

- 用户交互便捷性
- 程序功能丰富性和完整性
- 项目架构的鲁棒性和稳定性
- 程序运行效率

本次审查未修改业务代码。已执行的验证命令：

```bash
pnpm typecheck
pnpm build
cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
pnpm build:extensions
```

以上命令均通过。

## 总体结论

项目当前已经具备较扎实的 HTTP 下载核心：Rust 下载引擎、SQLite 持久化、Range 探测、分段下载、续传校验、队列调度、设置页、日志和浏览器 Native Messaging handoff 基础都已经存在。测试覆盖也比普通 MVP 更完整，特别是下载引擎和续传边界。

主要不足集中在三个方面：

1. 用户交互仍偏 MVP，命令面板、批量操作、错误恢复和高级诊断还没有形成完整闭环。
2. 功能完整度明显低于产品文档目标，浏览器接管、分类规则、托盘、通知、单任务限速、优先级等能力尚未完成。
3. 性能和发布安全边界还需要收紧，尤其是过高分片数、真实 App 中暴露 mock command、生产 CSP 和更新器配置。

最高优先级建议：

1. 移除或限制生产环境中的 mock 数据重置能力。
2. 收紧初始分片数和连接数上限，增加 per-host 限制。
3. 修正下载完成时覆盖同名文件的策略。
4. 补全真实命令面板和常用批量操作。
5. 用事件驱动替代活动下载期间的高频完整任务轮询。

## 1. 用户交互便捷性

### 1.1 当前已有优点

- 已有清晰的主界面结构：标题栏、命令栏、侧边导航、任务列表、详情面板、状态栏。
- 支持新建下载、URL 探测、选择保存目录、任务搜索、状态导航、任务详情、展开行详情。
- 已有 toast、删除确认、速度历史 sparkline、基础可访问性标签。
- 设置页已经包含保存目录、并发任务数、全局限速、多连接阈值、初始分片数、语言和浏览器集成状态。

### 1.2 主要不足

#### 命令面板仍是开发工具

当前命令面板只有“重置 mock 任务”，没有承载真实用户操作。这会导致 `Mod+K` 的入口存在感很强，但实际价值很低。

建议补齐：

- 新建下载
- 暂停选中任务
- 继续选中任务
- 删除选中任务
- 重试失败任务
- 打开文件
- 打开目录
- 复制下载链接
- 切换视图
- 打开设置
- 设置全局限速

#### 顶部限速按钮没有实际动作

命令栏中已经出现限速入口，但目前没有绑定行为。限速是下载器的高频能力，建议做成快速菜单：

- 不限速
- 512 KB/s
- 1 MB/s
- 5 MB/s
- 10 MB/s
- 自定义

设置页可以保留精确配置，但主界面需要更快路径。

#### 新建下载流程有重复等待

当前用户需要手动点击“Detect”，提交时后端又会重新 probe。用户体感上会经历两次等待。

建议：

- URL 输入停止 500-800ms 后自动探测。
- 显示探测状态、文件名、大小、是否支持续传。
- 提交时复用最近一次探测结果，或明确提示“正在重新验证资源”。
- 对探测失败提供“仍然尝试下载”的明确选择，仅限风险可控场景。

#### 设置项对普通用户不够友好

设置页中的全局限速和多连接阈值使用原始 B/s 和字节数。普通用户很难直接填写合理值。

建议：

- 限速输入支持 KB/s、MB/s、GB/s 单位。
- 分片阈值支持 MB/GB 单位。
- 常用值使用下拉或 segmented control。
- 对高级设置增加简短说明，但不要在主界面堆叠说明文字。

#### 错误恢复动作不足

失败任务和 `needs_attention` 任务目前能显示状态和错误信息，但缺少可操作恢复路径。

建议为错误状态提供：

- 重试
- 重新下载
- 另存为
- 打开目录
- 复制错误详情
- 复制下载链接

对于“远程文件已变化”这类场景，应明确告诉用户为什么不能直接续传。

#### 任务管理能力不完整

当前任务列表有搜索和基础状态筛选，但下载器常用管理能力还不足。

建议补齐：

- 排序：创建时间、更新时间、文件大小、进度、速度、状态。
- 批量操作：批量暂停、继续、删除、重试、打开目录。
- 更多筛选：文件类型、来源域名、失败原因、是否支持续传。
- 复制链接、复制文件路径。
- 重新下载同一 URL。

#### 详情页诊断深度不足

当前详情页包含 Overview / Chunks / Connections，但缺少文档中规划的日志、请求信息、错误时间线等内容。

建议补齐详情页 tab：

- Overview：基础进度、路径、URL、大小、平均速度。
- Chunks：分片范围、状态、重试次数、最后错误。
- Connections：真实连接速度、首包耗时、状态、最近错误。
- Logs：任务生命周期、重试、失败、恢复。
- Request：最终 URL、响应状态、关键响应头。

#### 连接速度展示不够真实

当前连接详情中的单连接速度是把任务总速度平均分配给活跃 segment，这对诊断服务器限速、慢连接、磁盘瓶颈没有足够价值。

建议后端维护 segment/connection 级速度，并通过事件或详情查询返回真实值。

## 2. 程序功能丰富性和完整性

### 2.1 当前已有优点

- HTTP/HTTPS 下载链路已经具备基础可用性。
- 支持大文件 Range 分段下载。
- 支持队列、并发任务数、全局限速。
- 支持基础浏览器 Native Messaging handoff。
- 支持浏览器集成安装状态展示。
- 支持应用更新检查入口。

### 2.2 主要不足

#### 协议类型仍然单一

当前只支持 HTTP/HTTPS。产品文档中提到的 BT、HLS、网盘解析、视频嗅探、插件协议等尚未实现。

建议短期不要立即扩展协议，而是先稳定 HTTP 下载。后续协议可按顺序推进：

1. HTTP 校验和批量导入。
2. HLS 下载。
3. BT 下载。
4. 插件协议或扩展协议。

#### 浏览器集成不是完整下载接管

当前扩展主要支持：

- 右键链接发送到 Vibe。
- 选中文本 URL 发送到 Vibe。
- 当前 tab URL 发送到 Vibe。

尚未支持：

- 自动捕获浏览器下载。
- 大文件下载接管提示。
- 从浏览器下载事件中接管。
- Cookie/header 转发。
- 站点级规则。
- 扩展内实时任务状态面板。

文档也明确 Safari、商店 ID、签名发布、WebSocket/localhost 实时面板仍未完成。

#### 浏览器发布链路未完成

Chromium extension id 仍是开发占位值，Firefox 也是本地开发 id。发布前必须完成：

- Chrome Web Store / Edge Add-ons / Firefox AMO 扩展 ID。
- Native Messaging manifest 中 allowed origins / extensions 替换为正式 ID。
- 扩展签名和审查流程。
- 安装引导和故障诊断文案。

#### 缺少下载器常见能力

以下能力在产品定位中很重要，但当前没有完整落地：

- 单任务限速。
- 单 host 最大连接数。
- 任务优先级。
- 文件类型自动分类保存。
- 批量导入 URL。
- 校验文件完整性。
- 下载完成系统通知。
- 系统托盘常驻。
- 开机启动。
- 关闭窗口后最小化到托盘。
- 任务标签。
- 历史任务归档。

#### 任务事件表尚未形成数据闭环

数据库中存在 `task_events` 表，但当前核心流程基本没有写入任务生命周期事件。因此详情页中的日志、错误时间线、重试历史还缺少数据基础。

建议定义统一事件模型：

- `task.created`
- `task.started`
- `task.progress_checkpoint`
- `task.paused`
- `task.resumed`
- `task.retrying`
- `task.failed`
- `task.completed`
- `segment.retrying`
- `segment.failed`
- `resume.blocked`

#### 自动更新配置已替换为真实仓库

Tauri updater endpoint 已配置为 `https://github.com/Chr0nixz/Vibe-Downloader/releases/latest/download/latest.json`。发布前仍需要验证签名、版本号、安装模式和回滚策略。

#### Mock 数据能力已限制在开发构建

`seed_mock_tasks` 已限制为 debug build 注册，前端命令面板也按 dev/runtime guard 显示。后续仍应在发布构建检查中确认生产环境无法调用 mock 清库命令。

建议：

- 仅在 `debug_assertions` 下编译和注册。
- 前端命令面板仅在 dev 环境显示。
- 生产构建中完全移除该 command。

## 3. 项目架构的鲁棒性和稳定性

### 3.1 当前已有优点

- 下载核心在 Rust 后端，UI 与下载逻辑边界清晰。
- SQLite 持久化任务和分片状态。
- Range 续传前会检查本地临时文件和远程元数据。
- 对远程文件变化有阻断策略，避免错误续传导致文件损坏。
- 分段下载有重试机制。
- 应用启动会重置中断中的任务状态，避免一直显示 downloading。
- Native Messaging payload 有版本、action、URL scheme 和嵌入凭据校验。
- 现有 Rust 测试覆盖了较多下载边界。

### 3.2 主要不足

#### 完成时同名文件覆盖策略有风险

下载完成时如果最终路径已存在，当前逻辑会先删除现有文件再 rename 临时文件。这可能覆盖用户在任务创建后放入的同名文件。

建议改为：

- 如果 final path 已存在，默认自动改名。
- 或进入 `needs_attention`，让用户选择覆盖、另存为或取消。
- 避免先删除再 rename 的非原子覆盖路径。

#### 生产安全配置需要收紧

当前 Tauri CSP 是 `null`。发布前应设置最小 CSP，至少限制默认资源来源和脚本来源。

建议：

- 开发配置可保持宽松。
- 生产配置使用单独 `tauri.prod.conf.json` 或按环境生成。
- 禁止不必要的外部脚本、iframe、远程资源。

#### 更新器发布链路不完整

更新器配置有公钥，但 endpoint 仍是占位。发布前必须实际跑通：

- 生成 `latest.json`。
- 验证签名。
- 验证 Windows/macOS/Linux 安装包。
- 验证失败时 UI 行为。

#### 续传校验策略仍可细化

当前校验 size、ETag、Last-Modified。后续可以增强：

- 区分强 ETag 和弱 ETag。
- 记录 `Content-Range` 验证信息。
- 记录服务器是否从支持 Range 变为不支持 Range。
- 对只有弱元数据的资源给出更明确风险提示。

#### 启动恢复策略偏保守

当前重启后下载中的任务会变成 paused，不会自动恢复。对于可靠下载器来说，这比“自动恢复”弱。

建议：

- 设置项增加“启动后自动恢复未完成任务”。
- 默认可保守关闭，向用户说明。
- 恢复前执行本地临时文件和远程元数据校验。

#### 错误模型不利于本地化和操作建议

后端当前大量返回英文字符串。中文界面下这些错误会直接显示英文，而且前端无法稳定根据错误类型提供操作。

建议后端返回结构化错误：

```json
{
  "code": "remote_changed",
  "message": "Remote file changed. Restart download to avoid corruption.",
  "recoverable": true,
  "actions": ["restart", "save_as", "copy_details"]
}
```

前端按 `code` 做本地化和操作展示。

#### Native Messaging handoff 文件写入可更稳

当前 native host 把 payload 写入临时目录，再启动主程序读取。建议增强：

- 写临时文件后原子 rename。
- 对同 request id 使用 create-new，避免覆盖。
- 主程序读取后无论成功失败都记录结果，并有清理策略。
- 定期清理过期 handoff 文件。

#### 生产权限面需要最小化

当前 Tauri capability 对主窗口开放了 `core:default`、`core:path:default`、`os:default`、`log:default` 等较宽权限。发布前建议逐项确认是否都必要，按实际 API 使用收缩权限。

## 4. 程序运行效率

### 4.1 当前已有优点

- 下载在 Rust 异步后端执行，不阻塞 UI 线程。
- 前端进度通过事件同步，而不是完全靠轮询。
- 大文件支持分段直接写入目标临时文件，避免最终合并 part 文件。
- 全局限速使用后端 token bucket。
- 构建产物有基础 manual chunks，前端主包大小可控。

### 4.2 主要不足

#### 初始分片数上限过高

设置页和后端都允许初始分片数到 256。下载启动时会对已有 segment 直接 spawn worker。若再叠加最多 8 个活跃任务，理论上可能产生大量连接和 worker。

风险：

- 本机连接数暴涨。
- 服务器触发 429/403/限流。
- SQLite 进度写入频率升高。
- UI 详情页渲染大量 segment。
- 全局限速下大量连接争抢 token，效率反而下降。

建议：

- 普通设置中最大初始连接数限制为 8 或 16。
- 高级配置中如果允许更高值，需要明确警告。
- 增加 per-host 最大连接数。
- 动态连接上限、初始连接上限、UI 配置上限使用同一套常量。

#### 动态加速上限和初始分片上限不一致

动态加速上限是 8，但初始分片可以到 256。这会让“动态保护逻辑”无法保护用户手动配置造成的连接爆炸。

建议：

- 把 `MAX_AUTO_SEGMENT_COUNT` 和用户可配置最大连接数统一设计。
- 命名上区分“segments”和“connections”。
- 已完成/未启动/活跃连接数分别建模，避免概念混淆。

#### 活跃下载期间存在重复同步

前端同时使用：

- 后端 `task.progress` 事件。
- 每 500ms `listTasks()` 完整轮询。

这会增加数据库读取、Tauri invoke、React store 更新和列表重渲染成本，也可能在 DB 落后事件时造成进度回退。

建议：

- 默认只使用事件更新活动任务。
- 队列变更、任务完成、失败时再刷新完整列表。
- 如果需要兜底同步，降低到 2-5 秒，并使用 merge 策略避免进度回退。

#### 任务列表没有虚拟滚动

当前任务列表直接渲染 filtered tasks。文档目标是 1000 个历史任务仍保持流畅，当前实现会受到以下因素影响：

- 每行都有 Framer Motion。
- 每行多个 Tooltip。
- 每行进度条和 speed sparkline。
- 状态更新可能触发大量 row 重新计算。

建议：

- 引入 `@tanstack/react-virtual` 或等价虚拟列表。
- 活跃任务可以置顶并独立小集合渲染。
- 历史任务分页或虚拟化。
- 降低非活跃任务的动画和 tooltip 成本。

#### 后端聚合进度频繁查询 segments

聚合进度时会查询当前任务所有 segment 并计算总下载量。分片数量高时，这会放大 SQLite 压力。

建议：

- 在下载任务内存状态中维护 segment downloaded map。
- 按节流周期批量落库。
- 完成/暂停/失败时强制 flush。
- 详情页按需查询完整 segment。

#### 详情页额外轮询 segment

打开 chunks/connections 时，前端每 2.5 秒拉取 segments。对于高分片任务，这会进一步增加数据库和渲染压力。

建议：

- 详情页订阅后端聚合事件。
- 只有打开详情页时后端才推送 segment 摘要。
- 后端返回分页或摘要，避免一次渲染大量 segment。

#### 数据库连接和写入策略可进一步优化

当前 SQLite pool max connections 为 5。下载进度、segment 更新、任务列表轮询、详情页轮询可能同时竞争连接。

建议：

- 明确写入节流策略。
- 使用事务批量更新 task + segments。
- 对高频 progress 只写关键 checkpoint。
- 增加数据库性能测试：多任务、多 segment、高速下载、频繁暂停恢复。

## 建议实施顺序

### P0：发布前必须处理

1. 生产环境移除 `seed_mock_tasks` command 和命令面板 mock 入口。
2. 收紧初始分片数和连接数上限。
3. 修正 final path 已存在时的覆盖策略。
4. 配置生产 CSP。
5. 替换 updater endpoint 占位并跑通更新链路。

### P1：核心体验完善

1. 补全命令面板真实操作。
2. 增加批量暂停、继续、删除、重试。
3. 新建下载自动探测并减少重复等待。
4. 错误状态提供恢复动作。
5. 设置页使用更友好的单位和预设。

### P2：可靠性增强

1. 引入结构化错误码。
2. 写入任务事件表，支撑日志 tab。
3. 增加启动自动恢复策略。
4. 增强 handoff 文件原子写入和清理。
5. 增加 per-host 连接限制。

### P3：性能优化

1. 任务列表虚拟化。
2. 去掉活动下载期间的 500ms 完整轮询。
3. 后端进度聚合改为内存状态 + 批量落库。
4. 详情页 segment 数据按需推送或分页。
5. 增加 1000 历史任务、8 活跃任务、大文件多分片的性能基准。

## 可量化验收标准

建议后续改进用以下指标验收：

- 1000 个历史任务下，列表滚动稳定保持 60 FPS 或接近原生滚动体感。
- 8 个活跃任务下载时，前端主线程无明显卡顿。
- 默认配置下单 host 连接数不会超过安全阈值。
- 下载完成时不会覆盖任务创建后出现的同名文件。
- 生产构建中无法调用 mock 清库命令。
- 失败任务至少提供一个具体恢复动作。
- 断点续传被阻断时，用户能看到明确原因和下一步操作。
- 浏览器扩展右键 handoff、重复 request id、App 已运行和未运行场景均可稳定处理。
